## 外部调用方视角：直接加载 DLL 调 GetApplicationAsync（14:2x）
- 用户要「直接用大模型调用这个类库中的 GetApplicationAsync 看执行情况」。做法：不写项目文件、不经过 xunit，用 `dotnet fsi --readline- --quiet --nologo` 从 stdin `#r` 引用 `xUnitHost/bin/Debug/net10.0/{OsHost,Autodesk.AutoCAD.Interop,Autodesk.AutoCAD.Interop.Common,AutoCADHost}.dll`（`AutoCADHost` 本体是 netstandard2.0，测试输出目录这一套依赖最齐），直接调 `GetApplicationAsync 27148`。只读，没改任何文件 / 状态。
- 实测：fsi 调用方主线程是 **MTA**（线程 2），照样 29ms 挂回成功 —— 库内部 `Sta.runAsync` 自己起固定 STA 线程（29），外部调用方不必准备 STA 公寓。返回的是 `Task<AcadApplication>`，拿到时 `IsCompleted=false`（真异步，不是已完成的假 Task）。
- 模型这一侧拿到的 `app` 是 `System.__ComObject`，`ToString()` 也只有 `System.__ComObject` —— **COM 代理不可序列化，模型读不出内容**。要读值得 `Sta.run (fun () -> app.Version)`，或直接用 `GetApplicationWithRootsAsync`（纯数据记录） / `describeByPid`（11 行文字）。三个入口实测都返回真值：版本 23.1s、Hwnd 657248、1 份图纸 Drawing2.dwg、Groups 5、IsQuiescent=True。
- 负例：给 fsi 自己的 PID 5240 → `IsFaulted=true IsCompleted=true`，await 抛 `InvalidOperationException：…拒绝挂回，绝不新建`。
- 补充实验：MTA 线程**不包 `Sta.run` 直接读 `app.Version` 也成功（3ms）**，没抛异常 —— 简单属性的跨公寓封送这次能完成；但口径不变，复杂 / 长时间 COM 操作仍回固定 STA 线程，别把「这次能读」当成可以裸用 RCW。
- 坑：`dotnet fsi` 从 stdin 执行完固定返回 1（极简 `printfn` 脚本也是 1），是交互模式收尾码，不是调用失败。
- 结论：类库作为独立 DLL 可被外部进程直接消费；若要正式挂给大模型当工具调用，别把 `AcadApplication` 跨边界传出去，应加一层返回纯文本 / JSON 的入口（现成可复用 `describeByPid` / `GetApplicationWithRootsAsync`），并把 faulted Task 的异常文案接成结构化错误。这层本次没做，等用户定。
- 现场：四家进程前后一致（WINWORD 26772 / EXCEL 19180 / acad 27148，POWERPNT 无），无 fsi 残留；工作区仍只有用户那两行 `executeAsync` 草稿未提交。

## 返回面语义对齐（14:4x）
- 用户总结：`exit=1` 是 fsi 的概念；`GetApplicationAsync` 这个任务只返回 `AcadApplication`、没有其他信息，要比对得靠其他渠道；失败时 Task faulted 且挂着一个 exn。**按「单次任务返回面」这个语义，用户是对的** —— 上一轮我把它读成「整个进程之后不能再读」，拿「同一进程里继续读了 Version / 11 行文字」去反驳，是理解偏了：那些都是另外发起的调用，正好印证「其他渠道」。
- 实证：`Task<AcadApplication>` 的 Result = `System.__ComObject`（`ToString()` 同），没有版本 / HWND / 图纸等任何字段；负例 `IsFaulted=true IsCompleted=true IsCanceled=false`，**`Task.Exception` 是 `AggregateException`，`InnerException` 才是 `InvalidOperationException`**；`await` / `GetAwaiter().GetResult()` 抛的是解包后的 `InvalidOperationException`，不是 AggregateException。
- 「其他渠道」清单：① 对该 RCW 再发 COM 调用（`Sta.run (fun () -> app.Version)`，属于新动作且须固定 STA）；② 类库另两入口 `GetApplicationWithRootsAsync` / `describeByPid`（**内部重新按 PID 挂回一次 `findOnSta`，不复用这次拿到的 app**）；③ OS 侧 `Proc.exePath` / `Process.Modules` / `FileVersionInfo` / `Win32.pidOfWindow`；④ 黑板文本本身。全都不在 `GetApplicationAsync` 的返回面里。
- 推论：只把 `GetApplicationAsync` 挂成大模型工具不够 —— 返回值跨进程边界读不出，后续工具也接不了这个 COM 代理；要么工具内部把值转成文本 / JSON，要么各工具各自按 PID 重新挂回。`describeByPid` 那种「一步给文字」的形状才是模型友好的。
- 本次只读探针，未改项目代码；输出末尾的 `Exit Code: 1` 仍是 fsi stdin 收尾码。

- 用户先要「写个 fact 用大模型在 AutoCAD 里画一个圆，还是用 task 包裹，不然调用者不知道什么时候结束」。首版真机跑撞 `0x80010001 RPC_E_CALL_REJECTED`（`Documents.Add()` 刚建完就 `AddCircle`，AutoCAD 界面流程还没走完），收尾 `Close` 也被拒、残留 `Drawing3.dwg`；带重试的只读探针把现场收回（只剩用户 `Drawing2.dwg`）。**用户随即叫停：「不用跑了，先需要在 autocad 控制接收命令的位置处设置一个消息订阅，当 autocad 通知你 ready 后你再发命令」**。
