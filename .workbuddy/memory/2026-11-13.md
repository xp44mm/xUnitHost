## OsHost.Sta 加固（18:0x）
用户问「这个模块是单例吗？要不要改成类 + 全局单例」。结论：是（模块静态构造 = CLR 保证只跑一次），
**不改成类**——状态就一条线程 + 一个队列，类化只多一层间接、多一个 `new` 出错的口子，还得放弃编译器给的唯一性。
动了三处（`OsHost/STA.fs`）：
- `run` 里加同线程检查：已在固定 STA 线程上还 `run` → 抛 `InvalidOperationException`（原来是自己等自己，永久卡死）。
  `runAsync` **不加**：它只入队不等，`EventPair`/`AcadAttachTest` 的「在 STA 上退订 `|> ignore`」正是靠这个行为。
- `let lazy started` → `lock startGate + let mutable worker`：`Lazy` 会把首次异常缓存住，一次 Start 失败就永久失败。
- 新增 `shutdown ()`：`Interlocked.Exchange closed` → `jobs.CompleteAdding()` → `Join`；之后 `run`/`runAsync`
  抛 `ObjectDisposedException`（`enqueue` 里把 `InvalidOperationException` 也翻译成它）。**不重启**：旧 RCW 随线程作废。
- 新 `xUnitHost/StaThreadTest.fs`（`-m "*STA*"`）：单例/先进先出/`here` 不换线程/自等报错（`-m "*STA 自等*"`）；
  关停那条 gated，`XUNITHOST_STA_SHUTDOWN=1` 单开一个进程专跑（会毒掉同进程后面的 Fact）。
- 验证：`dotnet build xUnitHost.slnx -v q` 0 警告 0 错误；`-m "*STA*"` 全过（顺带跑了 RxCommandTest 的
  openSession→exec→close 真机链路，说明改造没伤会话层）；关停单独进程 1 条过。
- 追加：`run` 里的 `TaskCompletionSource<obj>` + `box`/`unbox` 拆掉，改成强类型 `TaskCompletionSource<'T>` 直接捕获进闭包
  （`enqueue` 收的是闭包，本来不必转手 obj）。行为不变，`-m "*STA*"` 复跑全过。
  `run` 形式上就是 sync-over-async，但底下要搬的是**线程亲和性**不是并发 I/O，阻塞等是它的本体；`runAsync` 是另一语义（发了就走），两条都留。
- 再合并：`run` / `runAsync` 的重复逻辑抽成 `private schedule : (unit -> 'T) -> Task<'T>`（closed 检查 + 起线程 + TCS + enqueue），
  `run = refuseNesting(); (schedule work).GetAwaiter().GetResult()`，`runAsync = schedule`。同线程检查抽成 `refuseNesting`。
  注意：`run` 现在用的是 `RunContinuationsAsynchronously` 的 TCS —— 阻塞 `GetResult` 走的是 task 完成事件、没有续体，
  所以行为不变。`-m "*STA*"` + `-m "*STA 关停*"` 全过。
- 加 `OsHost/STA.fsi`（签名文件，本仓唯一一份；fsproj 里排在 STA.fs 之前）。对外只暴露 4 个：
  `run` / `runAsync` / `here` / `shutdown`，`schedule` / `refuseNesting` / `enqueue` / `startedThread` / `closed` 全成 private 不出现。
